# 任务 01：原生菜单重复右键响应优化

本报告记录系统根因修复前的应用优化与历史实测。后续已定位并隔离 PCAppStoreExt 的三秒状态查询，本机菜单问题于 2026-10-04 获用户确认解决；最终结果见 [系统修复验收报告](windows-lnk-menu-delay.md)。下文首次／失效后数秒等待是当时的限制。

## 原因与实测反馈

2026-10-04 用户继续报告右键到菜单出现需 3–4 秒，并要求继续未完成的优化。当前基线为 `9947248be210cfdfaa3521f1d7222831e1f1fcea`，保持 Folder 原地显示 Windows 原生传统完整菜单、没有红叉、不经过资源管理器的要求。

旧完整包只读检测实际 MSI Afterburner 快捷方式：首次准备 4092 ms，取得对象 78 ms、构建命令 3839 ms；再次准备 3107 ms，取得对象 2 ms、构建命令 3091 ms。WPF 最大停顿 47 ms。等待集中在 `IContextMenu.QueryContextMenu`，此前把调用移到 STA 线程解决了界面冻结，但没有消除命令准备时间。

隔离比较 `CMF_ASYNCVERBSTATE`、`CMF_ITEMMENU`、`CMF_DONOTPICKDEFAULT` 及无附加标志，重复构建均为约 3.2 秒；复用同一 `IContextMenu` 也约 3.2 秒。复用完整已构建原生 HMENU 的只读探针实际可见时间为 41／22 ms。采样的栈候选涉及 `BaseDataDrivenCommand.GetState` 与 COM 等待，不能据此断言某个具体第三方软件造成全部延迟。探针仅在忽略目录运行，没有注册组件、注入 Explorer、执行用户文件命令或改变扩展设置。

正式真实鼠标反馈命令：

```powershell
rtk proxy python -c "import subprocess; raise SystemExit(subprocess.run(['src/KageDesktopTool/bin/Release/net10.0-windows/KageDesktopTool.exe','--content-input-check','--menu-latency-only']).returncode)"
```

前期预构建检查曾从 4475 ms 降到 444 ms，但快速切换图标时发现额外等待，因此未作为最终策略。最终检查先实际打开并取消菜单，再测量重复右键；同时验证文件变动、过期和切换图标。

## 正式策略与边界

- 不主动后台查询其他图标，避免并发的 Shell 状态查询互相等待。只短期复用已经展示且用户仅取消的完整原生菜单；执行命令后立即释放，不复用其旧状态。
- 使用实际路径集合、Shift、文件创建／修改时间、大小、属性及剪贴板序号核对；系统偏好改变、Folder 销毁也失效。显示前核对后重新构建。
- 结果最多保留构建完成后的 5 秒，超时在所属 STA 释放 HMENU、COM 及 PIDL。重复取消不延长期限，其他未直接观察的动态状态也受该短期限约束。
- 仍使用原始 `IContextMenu2/3` 消息转发、系统命令 ID 和 `InvokeCommand`；保留单项／多项、Shift 扩展、重命名业务入口、真实取消与操作后刷新。

这项优化减少重复构建，**不会使 Shell 自身的 3–4 秒构建变快**。首次右键、执行命令后、选择或状态变化、缓存过期后仍可能等待；不能把这些路径标为瞬时响应。没有裁剪原生菜单、禁用用户扩展或修改全系统菜单设置。

## 验收进度

最终正式检查已通过：首次右键 4038 ms，取消后重复右键 **203 ms**（含实际鼠标按下／释放和检查等待）；文件变化后命令构建 3076 ms、过期后 3089 ms，均重新计算；另一图标直接右键 3248 ms，没有主动预构建造成的额外等待。实际 MSI Afterburner 只读诊断首次准备 3541 ms，重复准备 **2 ms**，UI 最大停顿 47 ms，无标题栏辅助窗口。

最终自包含完整包 `releases/任务01 菜单重复响应优化/` 的资源、菜单延迟／失效、原地／Esc／无红叉、完整内容输入、图标、准备取消和实际用户菜单诊断 **7 项串行检查均退出 0**。完整 58 组业务回归通过。最终包实测首次右键可见 4043 ms，取消后重复 201 ms；实际 MSI 菜单准备首次 3682 ms、重复 2 ms，界面最大停顿 48 ms。验证环境为本机 Windows 11、单屏 150% DPI，不声称硬件多屏已经实测。

试用前先从托盘退出旧版，然后运行新完整目录中的 `KageDesktopTool.exe`；不要只复制 EXE。旧正式包保留，未发布的预构建实验包已删除。

双轴初审共同指出匹配的未完成任务可能排在另一图标的同步构建后，原实现等待它会累加延迟。真实双快捷方式停留／切换检查失败，观察 **5524 ms**。仅改为独立线程直接构建仍为 **5536 ms**；两个隔离探针进程并发调用时，B 准备为 **5817／6160／6233 ms**，而 A 约 3–4 秒。说明本机这种同时调用会相互影响，不足以认定具体软件归因。已撤掉主动预构建，最终策略只复用用户实际打开且取消后的有效菜单，避免引入这种额外工作。

Standards 复审指出显示中失效后取消仍可能留存旧菜单的竞态。正式鼠标与缓存失效入口准确复现：失效后的再次构建为 **0 ms**，旧结果被复用，检查失败。修正记录构建时的失效代次，匹配／留存时核对，不依赖清理消息与原生菜单嵌套循环的先后顺序；修复后重新构建 **3074 ms**，检查通过。真实 Shift 变化后的扩展菜单重新构建也通过。

证据位于 `.scratch/desktop-folder/verification/`；隔离参数和完整菜单复用探针位于 `.scratch/native-menu-capability/classic-latency/`，仅诊断，不属于发布包。

## Standards

固定基线 `9947248be210cfdfaa3521f1d7222831e1f1fcea`。初审的队列等待、复审的系统失效后留存均通过真实输入先失败后修正；最终规范违例、正确性及可行动 heuristic 发现均为 0。最终实现 `9f55b13`，失效竞态修复 `4b057e7`。

## Spec

最终复审剩余发现 0。原地原生传统完整菜单、单项／多项、取消、刷新及无红叉保持；仅短期重复右键加速，首次／变化／过期仍可能数秒等待的限制准确记录，未以删减命令或修改系统扩展设置代替优化。
