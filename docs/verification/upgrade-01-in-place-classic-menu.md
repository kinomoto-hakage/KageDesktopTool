# 任务 01：原地原生传统菜单与界面响应

用户最新决定：接受 Folder 内原地展示的 Windows 原生传统完整菜单，要求解决卡顿与红叉。此前必须跟随 Windows 11 现代菜单的要求由本决定取代；停止内部现代菜单及桌面桥接实验，没有执行被拒绝的 COM 注册／Explorer DLL 加载。

## 修复与准确反馈

正式 Runtime 的反馈命令：

```powershell
rtk proxy python -c "import subprocess; raise SystemExit(subprocess.run(['src/KageDesktopTool/bin/Release/net10.0-windows/KageDesktopTool.exe','--content-input-check','--menu-placement-only']).returncode)"
```

修复前准确失败：右键 `(189,198)`，菜单却在 `(1603,350)`，且打开了真实内容目录的 Explorer 窗口。修复后通过：系统菜单从 `(189,198)` 展开，没有打开内容目录，允许屏幕边缘避让。

菜单通过公开 `IShellFolder.GetUIObjectOf`、`IContextMenu.QueryContextMenu` 和 `TrackPopupMenuEx` 取得与执行实际单项／多项对象的系统及第三方命令，不自绘替代菜单。保留 `IContextMenu2`／3 消息转发、Shift 扩展命令和实际调用点。重命名命令需要宿主提供编辑界面，沿用持久化 `RenameContentAsync` 业务边界；菜单操作结束仍刷新选择、项目与计数。

菜单构建及跟踪迁至单独 STA 线程，复用线程和 HWND；窗口为无标题栏、零尺寸的原生 popup，不创建 WPF ToolWindow，不打开文件管理窗口。取消消息带请求标识，避免已取消请求的迟到消息关闭后续菜单；准备阶段检查取消，正在显示的菜单通过宿主消息结束，不执行取消后的命令。

## 实际响应与限制

最初旧版在实际 MSI Afterburner 快捷方式测得准备约 **4186 ms**、WPF 最大停顿 **4159 ms**，带标题栏辅助窗口。当前测得首次准备 **3864 ms**、再次 **3083 ms**，WPF 最大停顿 **47 ms**，带标题栏辅助窗口 **False**；窗口类为原生传统菜单 **`#32768`**。

计时进一步区分：取得对象 **74／1 ms**，命令构建 **3778／3079 ms**。剩余准备时间主要在 Shell 命令扩展构建；本修复解决界面随菜单冻结和红叉，不能保证所有已安装扩展的菜单首次瞬间出现，也不会为缩短时间擅自移除命令或禁用系统扩展。这些是 Windows 11 单屏 150% DPI 的本机结果，不代表其他设备固定耗时。

诊断中的菜单通过取消消息关闭，不依赖其他程序焦点或向全局键盘反复发送 Esc；只读实际用户快捷方式，未执行其命令或修改其内容。原地／完整输入检查的文件命令仅作用于随机隔离夹具。
