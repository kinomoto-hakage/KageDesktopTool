## 阻塞关系

- 01 没有票据阻塞：在票内首先完成当前宿主的隔离可行性验证，再接通正式开关、绘制和事务。若无法提供真实背景模糊，应记录受阻行为，不能仅实现一个始终回退的开关后宣布完成。
- 02 依赖 01：需要可运行的效果、用户设置和正式预览入口，才能验证四向几何、多个实例及宿主生命周期。
- 03 依赖 01：需要已接通的效果与基本不可用状态，才能实现系统限制、提示和自动恢复。
- 02 与 03 互不阻塞：四向／宿主恢复可在无系统限制环境验收；系统限制与恢复可在已有上方布局验收。共享运行时模块不构成额外依赖，合并时协调变更，真实桌面输入检查串行执行。
- 后两票中最后完成的一票负责四向、Explorer 恢复与系统暂停／恢复的组合验收；这项最终组合检查不额外阻塞另一票开始。

## 粒度与实施约束

- 每票都交付用户可操作的完整行为，包含必要状态、业务、界面、平台接入和自身验证，不拆出单独的 schema、API、UI 或测试票。
- 当前没有必须先完成的广泛机械重构。需要整理背景层或资源生命周期时，在所属票内先保持原背景可运行，再增加效果。
- 01 的可行性验证是核心功能的前置步骤，不单独发布一张缺少用户交付的研究票。票内可分步提交，但完成标志是正式入口中可演示的真实效果。
- 02 完成后可独立演示四向与宿主恢复；03 完成后可独立演示系统暂停、提示与自动恢复。
- 延用规格中的 `IDesktopWorkspace` 业务验证边界与真实 Windows 桌面验收；用户已在本轮确认该边界。
- 多屏、混合 DPI、拔屏、省电硬件条件或动态壁纸未实际覆盖时明确记录；模拟环境轨迹与真实系统验证分开报告，不扩大验收结论。
- 票据发布不包含程序实现、版本发布、GitHub Release 或父规格关闭。
